# Go 20 / U1b-1 — The release channel for the CLI binary

Unit of the program `odd/tasks/go-20-python-exit.md` (U1, fourth slice). Base `a5bdce7`. Worktree
`.worktrees/go-20-u1b1-release`, branch `change/go-20-u1b1-release`.

## Specs
- S1 — Program decision S9 (verbatim option): "Release verificado + build local de respaldo". The
  installer and the engine both read the trust root at `<home>/bin/SHA256SUMS`, so this unit is what
  turns the download path from fail-closed into the default.
- S2 — The repository already has the whole discipline for the GATE: `scripts/build-gate.sh`
  (CGO_ENABLED=0, `-trimpath`, `-buildvcs=false`, four targets, go1.24.13 warning), a committed trust
  root with a documented header, `scripts/verify-gate-sums.sh` (canonical comparison) and a release
  workflow that builds a goos/goarch matrix, emits SHA256SUMS, compares it against the committed file
  and attaches the assets. The CLI gets the same shape, not a second invention.
- S3 — The CLI's trust root lives at `bin/SHA256SUMS` — the exact path U1b-2b's installer defaults to —
  and its assets are named `ai-specs-<goos>-<goarch>`, which is what `internal/upgrade.AssetName`
  already produces for the native path.
- S4 — The digest comparison for the CLI is its OWN script (`scripts/verify-cli-sums.sh`) rather than a
  parameter added to the gate's: `scripts/verify-gate-sums.sh` is pinned by a test
  (`tests/test_worktree_gate_release_phase4.py:238-242`) and by the release documents, so its
  two-argument contract is not touched. The duplicated logic is a handful of lines of `awk`/`sort`;
  the alternative was churning the checksum gate of an already-released artifact.
- S5 — Reproducibility is the point, and it is tested: with go1.24.13 and those flags, a local build of
  the host platform's asset must hash to the digest committed in `bin/SHA256SUMS`. That is the same
  promise the gate's header makes ("Reproduce any digest locally with …").
- S6 — No deletion, no behavior change in the installer: the download path simply becomes *possible*
  once an asset exists. A manifest whose `VERSION` has no published assets still falls back to the
  local build.

## Log (continued)
- L5 — Tooling gap recorded rather than worked around silently: the YAML was validated with macOS's
  system Ruby because neither PyYAML nor `actionlint`/`yq` is available in this environment. That is a
  weaker check than a linter — it proves the file parses and the jobs/needs/globs are what they should
  be, not that every GitHub Actions expression is valid. A CI-side parse/lint step belongs to the
  release-polish follow-up below.
- L6 — Follow-up, deliberately NOT absorbed into this unit: the release workflow still has no CLI-side
  parity corpus (the `parity` job runs the gate's). Adding one is a CI policy decision about what a tag
  may ship, not part of opening a download channel, and the repository currently runs no other CI at
  all.
- L7 — The digest discipline is a promise both directions: committing digests before the assets exist is
  safe precisely because the checksum job fails the release when CI's bytes differ from them. That is
  the gate's precedent (L3) and the reason this unit could land without publishing a release.
- L8 — The rename broke three tests (`tests/test_worktree_gate_release_phase4.py`, which pins that
  workflow path) — the THIRD time this session an artifact was moved without grepping every test that
  names it (`scripts/verify-gate-sums.sh` had been grepped, the workflow file had not). Sharpened rule,
  recorded in the program document as L11: enumerate every artifact the unit MOVES or renames, not only
  the ones it edits, and grep the test tree for each BY NAME. The three call sites were retargeted and
  the workflow name is now also corrected in the live references that carried it (the gate's trust-root
  header, `scripts/build-gate.sh`, `scripts/verify-gate-sums.sh`, `ai-specs/skills/release-flow/SKILL.md`).
- L9 — **The reproducibility test earned its place**: after those retargets, a fresh local build no
  longer matched the committed digest. Cause, established by reading `assets.go`: the CLI embeds
  `all:catalog`, `all:templates`, `all:bundled-skills` and `all:bundled-commands`, so
  `catalog/recipes/worktree-flow/bin/SHA256SUMS` — the GATE's trust root — is part of the CLI's bytes, and
  changing one comment inside it changed the binary. (`ai-specs/skills/...` is NOT embedded, so that edit
  was harmless.) The digests were regenerated after all embedded-tree edits and the rule now lives in
  `bin/SHA256SUMS`'s header: any change inside the embedded tree invalidates these digests and must be
  committed together with a regeneration.
