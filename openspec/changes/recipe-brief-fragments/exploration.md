## Exploration: recipe-brief-fragments

### Problem Statement

Today `AGENTS.md` is generated by `lib/_internal/agents-render.py` from two sources:
1. Structured values from `resolved-config.json` (board_id, integration_branch, test_command, vault_scope — all already derived from recipe configs)
2. Prose sections from the manifest's `[brief]` table (runtime_flow, context_sources, conflict_policy, workflow_rules, useful_commands, mcp_descriptions)

The structured values are already recipe-derived automatically. The prose sections are still fully hand-written. A project adopting ai-specs-cli that runs `ai-specs init` gets a nearly empty `AGENTS.md` — only the structured values, no behavioral guidance.

The richness in ai-specs-cli's own AGENTS.md (35+ lines of `[brief]` prose) exists solely because a human hand-wrote it. The key insight: that prose is DERIVABLE from the enabled recipes. `worktree-flow` implies worktree rules; `trello-mcp-workflow` implies "Trello controls work state"; `tdd-flow` implies "run the test command before verifying"; `vault-canonical-store` implies "Vault controls canonical decisions." This is the gap: recipes do not yet declare the behavioral prose that agents need.

### Decision 1: Fragment Schema — Inline TOML vs. Sibling File

**Options:**

A. **Inline TOML in `recipe.toml`** — add `[provides.brief]` table with per-section string arrays:
```toml
[provides.brief]
workflow_rules = [
  "Create a dedicated worktree for changes that write artifacts.",
  "Do not merge directly to the integration branch without a PR.",
]
context_sources = [
  "Trello is the source of truth for work state and dependencies.",
]
```

B. **Sibling `brief.toml` file** in the recipe directory:
```
catalog/recipes/worktree-flow/
  recipe.toml
  brief.toml   ← fragment declarations
```

C. **Sibling `brief.md` file** with section headers:
```markdown
## workflow_rules
- Create a dedicated worktree...
## context_sources
- Trello is...
```

**Analysis:**

| Factor | Inline TOML (A) | brief.toml (B) | brief.md (C) |
|--------|----------------|----------------|--------------|
| Validation | Parseable by recipe_schema.py | Separate parser needed | Complex markdown parse |
| Multiline prose | TOML multiline strings work | Cleaner for longer text | Native |
| Template substitution | Easy: `{config.integration_branch}` | Same | Regex-prone |
| Recipe authoring ergonomics | All in one file | Split concern | Familiar format |
| Redaction (secrets) | Not needed — fragments are prose | Same | Same |
| Incremental adoption | recipe.toml already being parsed | Extra file convention | Extra file convention |
| No side effects | `[provides]` section already exists | Needs new read path | Needs new read path |

**Recommendation: Option A (inline TOML under `[provides.brief]`).**

Rationale:
- `recipe.toml` is already parsed by `recipe_schema.py` and consumed by `agents-render.py` (via resolved-config). Keeping fragments inline avoids a second read path.
- String arrays in TOML (`["bullet 1", "bullet 2"]`) are well-suited to bullet-list prose. TOML multiline strings handle longer items.
- `recipe_schema.py` already has a `_parse_config` pattern; the same structural approach applies to `_parse_brief_fragments`.
- Multiline long prose that exceeds TOML ergonomics is a marginal case for brief bullets — if needed, fragments can use TOML multiline `""" ... """` strings.
- The "capability-awareness" (Decision 7) — substituting `{config.integration_branch}` — is directly expressible when the config is already merged alongside the brief.

### Decision 2: Which Brief Sections Are Recipe-Contributable vs. Project-Only

```
SECTION              RECIPE-CONTRIBUTABLE?  RATIONALE
──────────────────────────────────────────────────────────────────────────────
intro                NO                     Pure project identity/voice. No recipe knows the project's purpose.
purpose              NO                     Same as intro. Belongs in [brief].purpose only.
runtime_flow         YES                    Recipes define work patterns (worktree, SDD phases, tracker session).
context_sources      YES                    Recipes define what sources agents should trust (Trello, Vault, Engram).
conflict_policy      YES                    Recipes define precedence rules for their domain.
workflow_rules       YES                    Recipes impose behavioral rules (worktree gates, PR flow, TDD gate).
useful_commands      YES                    test_command already derived; recipes can add commentary/labels.
mcp_descriptions     PARTIAL                Recipe can provide a default description for its own MCP server.
                                            Project overrides via [brief.mcp_descriptions] remain.
```

**Project-only sections** (`intro`, `purpose`): Always taken from `[brief]` in manifest. If absent, section omitted.

**Recipe-contributable sections**: Recipe declares fragments; manifest `[brief]` augments or overrides.

### Decision 3: Merge Order and Determinism

**Challenge:** Multiple recipes each contribute bullets to the same section. What order?

**Options:**
- Recipe declaration order in manifest (the order `[recipes.*]` tables appear in ai-specs.toml)
- Recipe dependency/capability order (topological sort — complex, fragile)
- Explicit `order` / `priority` field per fragment entry

**Recommendation: Recipe declaration order in manifest** (the order `enabled_ids` are collected).

Rationale:
- `build_resolved_config()` already iterates `raw_recipes.items()` in manifest declaration order. Python dicts preserve insertion order (3.7+). This is stable and deterministic per manifest.
- The manifest author controls recipe order, so they implicitly control fragment order.
- No extra schema field needed. Simple.
- For ai-specs-cli itself: worktree-flow, git-pr-flow, session-context, tdd-flow, trello-mcp-workflow, vault-canonical-store — a natural ordering of foundational before specific.

**Implementation note:** `resolved-config.json` already carries `enabled` (list) and `recipes` (dict). Fragment collection should iterate `enabled` order, not `recipes.keys()` order (in case they diverge).

### Decision 4: Dedupe and Contradiction

**Problem:** `trello-mcp-workflow` and `vault-canonical-store` might both emit similar context_sources bullets about "source of truth." Two recipes cannot easily know about each other.

**Approaches:**
A. Trust recipe authors to write non-overlapping bullets (no dedupe)
B. Exact-string dedupe across all fragments before rendering
C. Fragment keys — each bullet has a `key` identifier; second declaration of same key is ignored

**Recommendation: Exact-string dedupe + capability-scoped fragment keys (hybrid).**

Specifically:
- Each fragment entry is a TOML inline table with `key` (optional stable identifier) and `text` (the prose):
  ```toml
  [[provides.brief.context_sources]]
  key = "trello-source-of-truth"
  text = "Trello is the source of truth for work state and dependencies."
  ```
- Simple string arrays (without `key`) are ALSO valid — for backward compat and simplicity:
  ```toml
  [provides.brief]
  workflow_rules = ["Create a dedicated worktree...", "Do not push directly..."]
  ```
- When merging N recipes: first occurrence of a `key` wins; duplicate `key` from later recipe is silently dropped.
- Exact-string match across keyless entries also dedupes (same text from two recipes → one bullet).

This gives recipe authors a way to declare "this bullet should be unique system-wide" while keeping the simple array form for non-conflicting bullets.

**Schema note:** Both forms must be supported:
```toml
# Simple form (array of strings):
[provides.brief]
workflow_rules = ["Rule A", "Rule B"]

# Keyed form (array of inline tables):
[[provides.brief.context_sources]]
key = "trello-source-of-truth"
text = "Trello is the source of truth for work state and dependencies."
```

Parser normalizes both to `{key: str|None, text: str}` internally.

### Decision 5: Precedence — Recipe vs. Manifest `[brief]`

**Current behavior:** Manifest `[brief]` is the ONLY source. Any section present in `[brief]` is used as-is.

**Proposed behavior with fragments:**

```
For each contributable section:
  1. Collect fragment bullets from enabled recipes (in declaration order, deduped)
  2. Collect bullets from manifest [brief].<section>
  3. Result = recipe_fragments + manifest_additions  (APPEND model)

Exception: if [brief] declares a section as override:
  [brief]
  workflow_rules.mode = "replace"   ← replaces recipe fragments entirely
  workflow_rules = ["Only these rules"]
```

**Recommendation: APPEND by default; REPLACE opt-in.**

Default (append): manifest `[brief].<section>` bullets are added AFTER recipe fragments. Most projects want to augment, not replace.

Override (replace): if the project needs to completely suppress recipe fragments for a section, they can opt in with:
```toml
[brief]
workflow_rules = ["Custom rule only"]
workflow_rules_mode = "replace"   # ← suppresses recipe fragments for this section
```

The `_mode` sibling key is a simple convention — no TOML structural change needed. `agents-render.py` checks `brief.get("workflow_rules_mode", "append")` per section.

**Why not REPLACE as default?** Because the whole point is that existing projects with hand-written `[brief]` MUST NOT change behavior — and they currently have no recipe fragments at all. When fragments are added, APPEND means they get recipe fragments BEFORE their existing bullets, which may surprise them. See Decision 6 for migration.

### Decision 6: Backward Compatibility and Migration

**Concern:** ai-specs-cli itself has ~35 lines of hand-written `[brief]` prose. When recipe fragments are added to `worktree-flow`, `trello-mcp-workflow`, etc., those fragments will prepend to the existing `[brief]` bullets → DUPLICATE CONTENT.

**Migration story:**

1. **Escape hatch already exists:** `<!-- ai-specs:runtime-brief -->` marker in AGENTS.md prevents regeneration entirely. Projects that need exact control keep this marker. ai-specs-cli itself currently uses this marker in CLAUDE.md (a symlink to AGENTS.md). No change needed.

2. **For projects WITHOUT the marker:** After this change, running `ai-specs sync` will produce an AGENTS.md with recipe fragments + manifest brief additions. If the manifest `[brief]` has content that overlaps with recipe fragments, duplicates appear. To clean up:
   - Remove the overlapping bullets from `[brief]` (they are now covered by recipe fragments).
   - OR set `workflow_rules_mode = "replace"` to suppress recipe fragments for that section.

3. **The canonical migration for ai-specs-cli itself:**
   - ai-specs-cli uses the `--preserve-if-runtime-brief` flag for its own AGENTS.md (which is CLAUDE.md via symlink containing the marker). That means the generated AGENTS.md is already a SEPARATE file that can be replaced freely.
   - The CLAUDE.md / AGENTS.md distinction means ai-specs-cli's "human runtime brief" is safe regardless.
   - The generated AGENTS.md (no marker) will get richer automatically after recipe fragments are added — which is exactly what we want for adopting projects to see as a reference.

4. **Init experience:** `ai-specs init` creates a new manifest. With recipe fragments, the first sync produces a meaningful AGENTS.md with recipe-derived behavioral guidance. The `[brief]` table in the scaffold becomes minimal (intro + purpose only). The template comment can explain: "Runtime flow, workflow rules, context sources, and conflict policy are contributed by your enabled recipes."

### Decision 7: Capability-Awareness / Template Substitution

**Problem:** `worktree-flow` fragment might say "Do not merge to `{integration_branch}` without explicit instruction." The recipe knows `integration_branch` from its config.

**Options:**
A. **Static prose only** — fragments are fixed strings, no substitution. Recipe authors write generic bullets.
B. **Python `str.format_map` substitution** — during render, substitute `{config_key}` placeholders from the recipe's merged config.
C. **Separate structured fields** — don't do substitution; instead recipes declare structured fields and the renderer formats them (like the existing `integration_branch` → `## Project` section pattern).

**Recommendation: Option B (light `str.format_map` substitution) with an explicit prefix namespace.**

Rationale:
- Some bullets are meaningfully more useful with real values. e.g.: "Do not push directly to `{integration_branch}`" becomes "Do not push directly to `development`".
- The merged config is already available during render (resolved-config.json carries `recipes.<id>.<key>`).
- Use prefix to avoid accidental substitution: `{config.integration_branch}` (not bare `{integration_branch}`).
- Substitution is best-effort: if a config key is missing, leave placeholder as-is (don't crash render).
- Fragment prose that doesn't use placeholders is unaffected.

**Implementation:** In `agents-render.py`, after collecting a fragment's text, apply:
```python
try:
    text = fragment_text.format_map({"config": merged_config})
except (KeyError, ValueError):
    pass  # leave as-is
```

**What stays static:** `intro`, `purpose`, and manifest `[brief]` bullets are NEVER substituted (they may contain `{` in backtick code).

### Decision 8: Init Experience — Floor of Quality

**Current floor:** `ai-specs init` creates a manifest with no `[brief]`. `ai-specs sync` produces an AGENTS.md with only structured fields (board_id, test_command, etc.) and MCPs — no prose.

**New floor (after this change):**

With the 6 recipes currently in ai-specs-cli's catalog, a project enabling `worktree-flow + tdd-flow + trello-mcp-workflow + vault-canonical-store` would get recipe-contributed bullets covering:
- **workflow_rules**: "Create a dedicated worktree for changes", "Do not push to `{integration_branch}` without a PR", "Run `{config.test_command}` before final verification"
- **context_sources**: "Trello is the source of truth for work state", "Vault stores canonical decisions and handoffs", "Skills are executable guidance..."
- **conflict_policy**: "Trello controls work state; Vault controls canonical decisions", "Proposed agent plans are lowest authority..."
- **runtime_flow**: "A session works on one explicit user request or Trello card", "Use worktrees for artifact phases"
- **useful_commands**: test_command already working; recipe can add a label line

The resulting AGENTS.md is meaningful without any hand-authored `[brief]`. The only sections needing project input are `intro` (who is this project?) and `purpose`.

**LLM-assisted `--rich` enhancer (optional, not required):**
A future `ai-specs sync --rich` flag could invoke an LLM to generate a project-specific `intro` and `purpose` from the project's README or package.json. This is additive and not a dependency of the core fragments feature. It fits naturally as a post-sync step that only populates the `intro`/`purpose` fields if absent.

**Template scaffold change:** The `ai-specs.toml.tmpl` template should reduce `[brief]` to only `intro` and `purpose` with a comment:
```toml
[brief]
intro = ""  # One-sentence description for the runtime brief header blockquote
purpose = ""  # One-sentence purpose shown in ## Project section
# workflow_rules, context_sources, conflict_policy, and runtime_flow
# are contributed automatically by your enabled recipes.
# Add bullets here only for project-specific additions or overrides.
```

### Key Risks

1. **Duplicate content for existing projects**: Projects with full hand-written `[brief]` will see recipe fragments prepended to their existing bullets. Migration requires either (a) removing now-redundant bullets from `[brief]`, or (b) using `_mode = "replace"` per section. The `--preserve-if-runtime-brief` escape hatch is always available but defeats the auto-generation goal.

2. **Recipe fragment quality / over-generality**: Fragments must be generic enough to be true for ALL projects using the recipe. "Do not push to `development`" is ai-specs-cli-specific; "Do not push to `{config.integration_branch}`" is generic. Recipe authors must write for all adopters.

3. **resolved-config size growth**: Adding `brief_fragments` to resolved-config.json increases the file size. With ~6 recipes, each with 3-5 bullets across 3-4 sections, this is ~30-40 fragment entries — negligible JSON.

4. **Test surface expansion**: `test_sync_pipeline.py` already has 1900+ lines. Brief fragment tests should go in a dedicated test file to avoid further inflation.

5. **Schema version / catalog compatibility**: Adding `[provides.brief]` as optional (no `[provides.brief]` = no fragments) means old catalog recipes without it continue to work. No catalog version bump needed.

---

### Approach Classification: Option A — `[provides.brief]` inline TOML in recipe.toml

**Summary of decisions:**
1. **Schema**: Inline TOML under `[provides.brief]` — both simple array form and keyed inline-table form supported.
2. **Contributable sections**: `runtime_flow`, `context_sources`, `conflict_policy`, `workflow_rules`, `useful_commands`, `mcp_descriptions` (default desc for the recipe's own MCP). `intro` and `purpose` remain project-only.
3. **Merge order**: Recipe declaration order in manifest (`enabled` list order). Deterministic, author-controlled.
4. **Dedupe**: Exact-string dedupe + optional `key` field for semantic dedupe. First-occurrence wins for same `key`.
5. **Precedence**: APPEND by default (recipe fragments first, then manifest `[brief]` additions). REPLACE opt-in via `<section>_mode = "replace"` in `[brief]`.
6. **Backward compatibility**: The `--preserve-if-runtime-brief` escape hatch fully protects hand-managed briefs. For generated ones, manifest `[brief]` bullets are appended after recipe fragments — no data loss, just potential duplication that requires cleanup.
7. **Capability awareness**: Light `str.format_map` substitution using `{config.KEY}` namespace. Best-effort (no crash on missing keys). Static prose (manifest `[brief]`) is never substituted.
8. **Init experience**: Recipe-enabled projects get meaningful AGENTS.md from first sync. `[brief]` scaffold reduced to `intro` + `purpose` only. Optional `--rich` LLM enhancer fits as a future additive.

### Open Questions

1. **`mcp_descriptions` recipe default**: Should a recipe provide a default description for its MCP server (e.g., trello-mcp-workflow provides "Trello MCP for project tracking"), overridable by `[brief.mcp_descriptions]`? The current renderer already has special `mcp_descriptions` logic — wiring a recipe default here is natural but needs a decision on whether `[brief.mcp_descriptions]` still takes full precedence or only project-specific entries override.

2. **Config substitution safety for code-bearing bullets**: Some workflow_rules bullets contain backtick code like "`./tests/run.sh`". If a recipe uses `{config.test_command}` in a bullet that also contains other `{...}` (e.g., bash brace expansion), format_map may misfire. Recommendation: escape policy — `{{` / `}}` for literal braces in fragment text.

3. **Fragment inheritance via recipe dependencies**: Currently recipes have no dependency/inheritance relationship. If a future recipe `sdd-tdd-flow` depends on `tdd-flow`, should it inherit `tdd-flow`'s fragments? Recommendation: No — fragments are per-recipe, inheritance would add complexity. Recipe authors should declare their own relevant fragments.
