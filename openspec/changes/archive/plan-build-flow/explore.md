## Current State

**Recipe mechanics (`catalog/recipes/`)**: a recipe is a `recipe.toml` (validated by `lib/_internal/recipe_schema.py`) that can `provide`: skills (bundled or dep), commands (`.md` prompt files materialized as native slash commands per runtime), MCP presets, templates (materialized with `not_exists`/other conditions), docs, `[[capabilities]]` (abstract role, e.g. `tracker`, `test-runner`), `[[provides.hooks]]` runtime lifecycle hooks (`pre-tool-use`, `post-tool-use`, `session-start`, `stop` — mapped per-harness by `lib/_internal/hooks-render.py`, normalized JSON-stdin/exit-code contract per `docs/runtime-hooks.md`), a sync-time `[[hooks]]` table (`event = "on-sync"`) with a **fixed action enum** currently limited to `validate-config`, `bootstrap-board`, `link-trello-card`, `sync-card-state`, `comment-verification` (see `lib/_internal/recipe-materialize.py:453-498`; unknown actions are warned-and-skipped), a `[config.*]` schema (required/type/default/enum/regex validation), an optional `[init]` workflow (one-time setup prompt, `needs_manifest`, `needs_mcp`), and `[provides.brief]` fragments that get woven into the generated `AGENTS.md` runtime brief (`runtime_flow`, `context_sources`, `conflict_policy`, `workflow_rules`, `useful_commands`, `mcp_descriptions` — `intro`/`purpose` are project-only and rejected from recipes).

Two recipe tiers exist (`docs/capabilities.md`): **foundational** (tool-agnostic pattern, e.g. `worktree-flow`, `tdd-flow`, `session-context`) vs **specific** (concrete vendor integration providing a capability, e.g. `trello-mcp-workflow`, `vault-canonical-store`). `worktree-flow` (reference pattern for this change, PR #103) shows the pattern of a foundational recipe with `[config.gate_mode]` (`enum = ["always","ask","off"]`, default `"always"`) resolved at sync time and stamped into a materialized runtime hook script (`hooks/worktree-gate.sh`) — i.e. config → stamped behavior, not a runtime decision each time.

**Where SDD/OpenSpec ceremony surfaces today**: it does NOT surface inside `ai-specs-cli` itself as a product feature. `openspec/changes/archive/2026-05-18-docs-remove-sdd-refocus/proposal.md` documents a deliberate, already-executed decision: *"SDD/OpenSpec code was removed from the product (now handled by gentle-ai)... This creates confusion — users see SDD commands and concepts that don't exist in the product."* That change deleted `docs/ai/sdd.md`, `catalog/skills/openspec-sdd-conventions/SKILL.md`, the `[sdd]` manifest section, and the "SDD (Spec-Driven Development)" key concept from `README.md`. The current `README.md` states explicitly: *"Agent orchestration (multi-phase planning, multi-model sub-agents, profiles) is handled by gentle-ai. `ai-specs` focuses on the spec layer and tool integrations (recipes)."* Earlier history in this repo's own `openspec/changes/archive/` shows the project built (`2026-04-26-sdd-integration`, `2026-04-30-definir-sdd-adaptive-contract`) and then walked back native SDD before landing on this boundary — this is not a one-off opinion, it's an iterated architectural decision.

Separately, the actual SDD ceremony machinery the current session is running under (explore → propose → spec → design → tasks → apply → verify → archive, with `sdd-init`, `sdd-continue`, model-assignment table, Engram topic-key conventions) is itself gentle-ai's global skill/orchestrator layer (`~/.claude/skills/sdd-*`), not anything shipped by this repo's catalog. `ai-specs-cli` recipes today (e.g. `trello-mcp-workflow`) already assume an SDD-shaped world exists around them (its `recipe.toml` description says *"Automated Trello board integration for ai-specs SDD workflows"* and its skill inspects "the active Trello card" for state), but the recipe itself contains no SDD ceremony logic — it just consumes/produces state (Trello cards) that an external orchestrator manages.

`catalog/recipes/session-context/skills/context-precedence/SKILL.md` explicitly lists "SDD/spec artifacts" under **canonical docs** in its precedence order, confirming SDD artifacts are an expected-but-external context source, not something this repo's recipes generate today.

## Affected Areas

- `catalog/recipes/` — new recipe directory needed (`recipe.toml`, `skills/<id>/SKILL.md`, `commands/plan.md`, `commands/build.md`, optionally `templates/`, `README.md`).
- `lib/_internal/recipe_schema.py` — only needs changes if the design requires a new `[[hooks]]` on-sync action (e.g. directory-existence validation) or a new config validation shape; a pure skill+command recipe needs zero schema changes.
- `lib/_internal/recipe-materialize.py:453-498` — the on-sync hook action dispatcher; adding a new action (e.g. `validate-artifact-dirs`) requires a new `elif` branch here plus a schema/doc update. Confirmed: **no existing action validates filesystem directory presence** — `validate-config` only checks the config schema's `required` fields (lines 453-480).
- `docs/recipes-catalog.md`, `docs/recipe-schema.md`, `docs/runtime-hooks.md` — would need a new catalog entry and any new hook-action documentation.
- `README.md` / `openspec/changes/archive/2026-05-18-docs-remove-sdd-refocus/*` — the prior decision to strip SDD language from user-facing docs is the direct precedent this change must reconcile with; the proposal phase should explicitly address why this is different (packaged as opt-in catalog content instead of core CLI capability) rather than silently reversing it.
- `ai-specs/skills/` (this repo's own dogfood config, generated via its own `ai-specs sync`) — not a place to add SDD content per the removal decision's "Out of Scope" note.
- Untracked `openspec/changes/worktree-flow-modes/` leftover from the prior merged-but-unarchived change — noted, not touched.

## Approaches

1. **Skill/instructions-only recipe (no config, no hooks)** — Ship a skill (`SKILL.md`, `auto_invoke` triggers) plus two commands `/plan` and `/build` that are pure prompt files instructing the agent to run the full gentle-ai SDD ceremony under the hood (explore→proposal→spec→design→[tasks] for `/plan`; apply→verify→[archive] for `/build`), while never mentioning OpenSpec/SDD terms to the user in the command's own visible output.
   - Pros: zero schema/materializer changes; fastest to ship; matches how `tdd-flow`/`worktree-flow` already package "discipline" as skill+command; keeps `ai-specs-cli` in its "spec layer + tool integrations" lane per README, delegating actual multi-phase orchestration to gentle-ai (no re-implementation, no conflict with the 2026-05-18 decision since no ceremony *logic* lives in `ai-specs-cli` — only a thin naming/UX wrapper around an existing external orchestrator).
   - Cons: fully dependent on gentle-ai's global skills being installed and active in the target project; if gentle-ai is absent, `/plan` and `/build` are empty promises with nothing to invoke; hard to test/verify materialization beyond "files exist"; artifact-store selection has to be re-derived by the agent each time rather than pinned by recipe config.
   - Effort: Low.

2. **Recipe with config schema + stamped on-sync validation hook** — Add `[config.artifact_store]` (enum `engram|openspec|hybrid`) and/or `[config.change_naming]` to `recipe.toml`, and a new on-sync hook action (e.g. `validate-plan-build-setup`) that checks required directories/MCPs exist (mirrors `worktree-flow`'s config→stamped-hook pattern and `trello-mcp-workflow`'s on-sync actions).
   - Pros: makes the "two verbs" contract explicit and inspectable in the manifest; config is validated once at sync time instead of trusted to agent judgment every session; closest to the Trello card's sketch.
   - Cons: requires new `RecipeValidationError` paths in `recipe_schema.py`, a new branch in `recipe-materialize.py`'s hook dispatcher, and new docs — nontrivial schema surface for something whose actual "work" (running SDD phases) still happens entirely outside this repo; risks scope creep into "core logic" territory that the hard constraint (catalog recipe, not core logic) is meant to avoid.
   - Effort: Medium.

3. **Per-runtime slash-command templates that call the native SDD dispatcher directly** — `/plan` and `/build` commands shell out to (or instruct the agent to invoke) `gentle-ai sdd-continue`/`sdd-status --json` when available, falling back to the prompt-driven ceremony otherwise, with the recipe's `[provides.brief]` documenting only "plan" and "build" as user-facing concepts.
   - Pros: reuses gentle-ai's own native dispatcher and JSON status contract, so `/build` naturally maps to `nextRecommended` states instead of re-deriving phase order; keeps this repo's recipe as a thin adapter, consistent with the README boundary.
   - Cons: couples the recipe to gentle-ai's CLI binary being installed/callable and to its JSON contract remaining stable — an external dependency risk this repo doesn't otherwise take on; needs explicit fallback behavior definition for projects without gentle-ai or without engram.
   - Effort: Medium-High.

## Recommendation

Approach 1 (skill/instructions-only recipe) as the first slice, with the artifact-store selection deferred to whatever the ambient orchestrator (gentle-ai) already resolves per its own Session Preflight — do not duplicate that state in `ai-specs-cli` config. This is the only approach that cannot violate the hard constraint ("catalog recipe, not core logic") or the 2026-05-18 architectural boundary, because it adds zero new schema/materializer surface: it is pure prompt content that tells the agent "when the user says plan/build, run the ceremony you already know how to run, don't surface OpenSpec/SDD terms." Approach 2's stamped validation hook can be proposed as a fast-follow once real-world usage shows a concrete failure mode that only a sync-time check can catch — do not build it speculatively. Approach 3 should be revisited only if/when this repo takes an explicit, versioned dependency on the gentle-ai CLI binary being present.

## Constraints and Open Questions (to resolve at proposal time)

- **Naming collision with removed concepts**: the recipe must not reintroduce `[sdd]`-shaped manifest sections or docs that look like the deleted `docs/ai/sdd.md` — the proposal should explicitly state how this differs from what was removed (opt-in catalog content vs. core CLI feature; user-facing vocabulary is "plan"/"build" only, never "SDD"/"OpenSpec"/"spec-driven" in any generated brief text). Note the Trello card names the recipe `sdd-plan-mode`, which itself contains "sdd" — the proposal must decide between card fidelity and vocabulary hygiene.
- **Mapping ambiguity**: "plan" plausibly = explore→proposal→spec→design→tasks and "build" = apply→verify→(archive). Whether `archive` belongs to `build` or is a separate implicit third step needs an explicit decision — the card sketches Archive as a distinct third stage (vault summary + Trello comment).
- **Worktree-flow interaction**: "plan" can run without a worktree (nothing written beyond artifacts), but "build" (apply) always writes files and must run in a worktree. The recipe's `/build` command instructions must defer to `worktree-flow` when both recipes are enabled — likely expressed as a `workflow_rules` brief fragment cross-reference, not a hard runtime dependency (recipe schema has no `requires` field, only capability convention).
- **Projects without gentle-ai / without engram**: the recipe cannot assume gentle-ai's skills or Engram MCP are installed. Behavior must degrade to "run through the phases as a single agent conversation, no persistence" rather than fail or silently skip ceremony.
- **Auto artifact-store/change-naming selection**: hiding OpenSpec from the user means the recipe/skill must derive a change slug and pick engram vs. openspec vs. hybrid without asking the user SDD-specific questions — needs a concrete default policy documented in the skill.
- **Card feasibility gap (verified)**: the card's "Hook: on-sync → validate-config (verifies spec/design/tasks dirs)" does not match current materializer capability — `validate-config` only checks required config fields. Either the hook is dropped from scope (Approach 1) or a new action must be added (Approach 2).

## Risks

- Reintroducing SDD-flavored naming into `ai-specs-cli` catalog content risks the user confusion the 2026-05-18 change was explicitly trying to prevent, if the "plan"/"build" abstraction leaks OpenSpec/SDD vocabulary anywhere in generated `AGENTS.md` brief text or doc output.
- Coupling a catalog recipe's correctness to an external tool's (gentle-ai) internal behavior/version is untestable from within this repo's own test suite beyond "files materialize correctly."
- Known unrelated limitation (issue #104): template fixes never reach already-synced consumers (`not_exists` condition) — relevant if this recipe ships template files that need revision after initial rollout.
