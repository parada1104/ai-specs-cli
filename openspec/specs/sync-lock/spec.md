# sync-lock Specification

## Purpose

Define `ai-specs/.ai-specs.lock` as a CLI provenance stamp that travels with a
fresh clone. The lock records which CLI version last synced the project and may
carry scoped integrity records for CLI-owned override targets; it is not a
general integrity manifest for committed content.

## Requirements

### Requirement: Lock is a provenance stamp

`ai-specs/.ai-specs.lock` SHALL record CLI provenance — `[meta]` with
`cli_version` and `synced_at` — plus `[agents.*]` generated-file hashes used by
`doctor`'s stale-file check. It MAY record `[managed."<project-relative-path>"]`
entries for CLI-owned governed overrides. Managed entries SHALL contain the
normalized SHA-256 of the bytes last written by the CLI and MAY contain recipe,
source, kind, and effective policy provenance. It SHALL NOT contain per-file
content hashes for skills or recipes, and SHALL NOT contain `[commands]` or
`[opted-out]` sections. The lock is the CLI-provenance signal that travels with
a fresh clone (the machine-local cache `meta.toml` does not).

#### Scenario: Lock contents after sync

- **WHEN** `sync` (or `init`) completes on a project with no governed overrides
- **THEN** `.ai-specs.lock` contains a `[meta]` table with `cli_version` and
  `synced_at`
- **AND** it contains no `[skills.*]`, `[recipes.*]`, `[commands]`, or
  `[opted-out]` sections

#### Scenario: Lock records managed override after template seed

- **WHEN** sync materializes a governed `condition = "not_exists"` template
- **THEN** `.ai-specs.lock` contains a `[managed."<target>"]` table with
  `sha256` equal to the normalized bytes written
- **AND** it still contains no skill/recipe/command hash sections

#### Scenario: Legacy command hash sections dropped on migration

- **GIVEN** a `.ai-specs.lock` written by a prior CLI version with `[commands]`
  and `[opted-out]` sections
- **WHEN** `sync` (or `refresh-bundled`) runs
- **THEN** those sections are removed
- **AND** `[meta].cli_version` is updated to the running CLI version
- **AND** valid `[managed.*]` entries are preserved

### Requirement: Lock is not an integrity manifest for committed content

The lock SHALL NOT be used to detect user edits of committed content; git is the
integrity/diff source for the committed project surface. Version-drift detection
in `doctor`/`upgrade` SHALL read `[meta].cli_version` only. `[managed.*]` is a
scoped exception used solely for governed override ownership classification and
SHALL NOT reintroduce skill, recipe, dependency, or command hashes.

#### Scenario: Doctor reads version from meta

- **GIVEN** a project whose `.ai-specs.lock` `[meta].cli_version` is older than
  the installed CLI
- **WHEN** `doctor` runs
- **THEN** it reports version drift based on `[meta].cli_version`
- **AND** it does NOT compute per-file skill/recipe hashes

### Requirement: Ownership records for generated artifacts

The lock SHALL carry the ownership records that license `sync`'s pruning
(`sync-ownership`, S3 "borrar siempre lo gestionado"), so deletion authority
survives a run and is never inferred from file content alone. All keys are
project-relative POSIX paths. `internal/lock/lock.go` is the shape authority:

- `[managed."<path>"]` — `sha256` of the bytes last written plus optional
  `recipe`, `source`, `kind` and `policy`. `kind` is one of `template`, `gate`,
  `runtime-brief`, `doc` or `recipe-command`: a recipe command copy is recorded
  with `kind = "recipe-command"` and the sha256 of the generated copy. The
  record is the ownership proof, so a disabled recipe's recorded copy is
  deleted even when its bytes were edited in an earlier run; a copy that
  changes after it was planned in the current run keeps both the file and the
  record for the next sync. A record whose artifact is already gone is
  dropped; entries with no owning recipe (the runtime brief) always survive.
- `[hooks]` — generated runtime-hook shim path → the owning hook's managed id
  (`ai-specs:hooks:<recipe>:<id>`). This record, not the `GENERATED by
  ai-specs` marker, is what licenses deleting a shim. A record whose shim is
  absent is dropped on the next sync.
- `[mcp."<target>"]` — server name → sha256 of the rendered entry for that
  agent MCP config target. Only a recorded server may be replaced or removed
  by sync; the table is emitted even with no servers, as the "looked, nothing
  managed here" marker behind the one-time unrecorded-server notice.
- `[mcp-block."<target>"]` — `sha256` of the exact managed-block bytes last
  written into a Codex TOML target (begin marker line through end marker line).
  Any difference means the user edited ai-specs' block, which sync refuses to
  rewrite.
- `[deps.<id>.skills.<skill>]` — dep content hashes kept for drift detection;
  the manifest's declared dep set, not the filesystem, decides which records
  are pruned.

The lock SHALL NOT emit the legacy `[recipes.*]` and `[skills]` tables: they
are still read for compatibility, but neither survives a write. The per-skill
ownership record of a still-enabled recipe deliberately lives in the CLI cache
(`<cache>/.recipe/<recipe>/.ai-specs-owned-skills`), not the lock, so lock bytes
stay compatible. Sections are
written in a fixed order (`[meta]`, `[managed.*]`, `[mcp-block.*]`, `[hooks]`,
`[deps.*]`, `[agents.*]`, `[mcp.*]`) with sorted keys.

#### Scenario: Recipe command ownership

- **GIVEN** a command copy recorded as `[managed."<agent>/commands/<id>.md"]`
  with `kind = "recipe-command"`
- **WHEN** the owning recipe stops being enabled and `sync` runs
- **THEN** the copy is deleted and its record removed, even if the user edited
  the copy in an earlier run (the record, not the file hash, is the ownership
  proof)
- **AND** a copy whose content changed during that same run is kept together
  with its record for the next sync

#### Scenario: Hook shim ownership survives an edit

- **GIVEN** a generated hook shim recorded in `[hooks]`
- **WHEN** the user edits the shim and then disables its recipe
- **THEN** sync deletes the shim and drops its `[hooks]` record

#### Scenario: MCP ownership is per server

- **GIVEN** a target with `[mcp."<target>"]` recording the servers ai-specs wrote
- **WHEN** a recorded server leaves the manifest
- **THEN** that server is removed from the target and from its record
- **AND** an unrecorded user server in the same file is never touched

#### Scenario: Hand-edited Codex block refuses

- **GIVEN** a `.codex/config.toml` managed block whose bytes differ from
  `[mcp-block."<target>"]`
- **WHEN** sync would rewrite or prune that block
- **THEN** it exits 1 with one error line and leaves the file and the MCP
  record byte-identical

#### Scenario: Legacy recipe and skill tables never come back

- **WHEN** `sync` (or `refresh-bundled`) writes the lock
- **THEN** `.ai-specs.lock` contains no `[recipes.*]` and no `[skills]` table,
  even after a recipe skill was materialized in that run
